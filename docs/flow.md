# 工作流程：一件事从进来到结束

> 状态：设计稿（2026-11-09）；§6 的两处减少打扰已确认。按现有渠道和 agent 设计，对象和状态的定义见 `router-worker.md` §2。和现在行为不同的地方在 §6 单独列出。

## 1. 总流程

```
① 接入        ② 路由（Router）                    ③ 执行（Worker）      ④ 交给 Yi                 ⑤ 收尾
渠道 ─Event─▶ 去重 → 过滤 → 指令 → 归属 → 攒批 → 分诊 ─▶ Task(todo) ─▶ 认领 → Run → 产出 ─▶ in_review / blocked ─▶ Yi 操作 ─▶ done / cancelled
                 │       │       │                                            │ 不需要 Yi            │ 改写 / 追问 / 批准
                 ▼       ▼       ▼                                            ▼                      ▼
               忽略   直接操作  追加到已有 Task                                 done                  新 Run（回到 ③）
```

三条原则：

1. **一件事一个 Task，一个 Task 一张卡片。** 同一件事的后续消息、改写、追问、审批都追加到这个 Task 上，飞书卡片原地更新，不新发。
2. **Router 只决定「这是哪件事、交给谁」，Worker 只决定「做成什么样、要不要 Yi」。** 两边互不越界。
3. **以 Yi 的身份发出去的东西，必须 Yi 点头**（不变）。

## 2. 按来源

| 来源 | 怎么进来 | 归属键（thread） | Router 交给 | Worker 产出 | 等 Yi 做什么（need） | 怎么结束 |
| --- | --- | --- | --- | --- | --- | --- |
| 飞书私聊、群里 @Yi | 用户身份轮询 | 话题 `lark:<chat>#<thread>`；无话题时只认未关闭的 Task | 分诊：助手 ack / answer / deep | 表情、草稿（结论 + 证据 + 建议回复）、无需回复 | send | 发出 / 不发 / 完成 / Yi 亲自回复 |
| 消息里带 MR 链接 | 同上 | `gitlab:<项目>!<iid>` | 规则：助手 mr 档，先回 Get | 评审报告 + 评论台账 | send（发到 MR） | 评论发出 / 不发 |
| 飞书项目评论 @Yi | meegle 轮询 | `meego:<工作项>`，工作项挂了需求就带上 storyId | 分诊：助手 | 草稿（回到工作项评论） | send | 同飞书消息 |
| 群里机器人 @Yi 的告警 | 轮询时识别 | `alert:<chat>` | 规则：按群攒批（2 分钟没新的或满 10 分钟），交给 alert | 一批的结论：同根因合并、只挑需要 Yi 处理的 | read；全部已恢复则直接 done | Yi 看完点完成；1 小时内同群再来就追加 |
| 定时任务 / 需求巡检 | cron | `cron:<任务>`，每次一个 Task | 配置指定：助手 deep；上次还在跑、或巡检时 Claude 5 小时额度已用 ≥ 80%（`PATROL_PAUSE_AT`）就忽略 | 和上一次比的变化 | read；没有变化直接 done，不推卡片 | 看完点完成 |
| 看板派活、草稿转任务 | 看板 | `board:<任务>` | 配置指定：dev；草稿转任务是同一个 Task 换成 dev | worktree 里的提交 | send（推送建 MR） | 推送 / 放弃 |
| 私聊机器人 | 长连接 | — | 引用卡片的「发 / 改 / 不发 / 完成」「记住」：直接操作，不建 Task；引用任务通知：追加到那个 Task；直接提问：新 Task，助手 deep | 机器人直接回答 | — | 答完即 done |
| Webhook（P5） | `POST /hooks/:name` | 按配置映射 | 按配置 | 按配置 | 按配置 | — |

写操作审批不是来源，是执行中途的一站：Worker 提出写操作 → Task 转 blocked、need=approve → Yi 批准后 cabinet 执行，结果追加到 Task → 回到 todo，Worker 接着跑。

## 3. Router 的判定顺序

每条 Event 按顺序走，命中一步就停：

| 步 | 判什么 | 结果 |
| --- | --- | --- |
| 1 去重 | `${channel}:${id}` 见过 | 丢弃 |
| 2 过滤 | 自己发的、机器人自己的卡片、PagerDuty `[Ack]` / `[Res]`、Yi 已经亲自回了 | 忽略，记原因 |
| 3 指令 | Yi 对已有 Task 的操作：引用卡片回复、看板按钮、「记住」 | 直接作用到 Task，不排队 |
| 4 归属 | thread 或正文提到的 MR 命中一个 Task：未关闭的直接追加；话题 / MR / 工作项在关闭后 3 天内也重开 | 追加：在跑就插话，空闲就回到 todo |
| 5 攒批 | 这个来源配置了攒批（告警按群；同一人连发几条） | 等收口后合成一个 Task |
| 6 分诊 | 先规则（MR → mr 档；cron、看板、webhook 按配置），再 luna 判档位 | 新 Task(todo)，带 title、worker、tier、priority |

Yi 正在这个聊天里聊（现在的 `waitIfYiActive`）：Task 照建，带一个「最早开始时间」，排队里显示「等你先回」，可以点「立即处理」。

## 4. Task 状态

```
            ┌──────── 同一件事来了新消息 / Yi 改写、追问、批准 ────────┐
            ▼                                                          │
 新事 ─▶ todo ─认领─▶ in_progress ─┬─ 要 Yi 过目 ─▶ in_review ─────────┤──▶ done
                                  ├─ 要审批 / 拍板 / 失败 ─▶ blocked ──┘
                                  └─ 不需要 Yi ─▶ done
 任意未关闭 ── Yi 不发 / 放弃 ──▶ cancelled
```

| 状态 | 看板分组 | need 举例 |
| --- | --- | --- |
| todo | 排队 | — |
| in_progress | 进行中 | — |
| in_review | 等我 | send 待发送、read 看结论 |
| blocked | 等我 | approve 待审批、decide 要你拍板、retry 失败 |
| done / cancelled | 今天完成 | — |

**飞书卡片只在 Task 进入 in_review / blocked 时推**；同一个 Task 再进入时更新原卡片并重新提醒。卡片和看板操作的是同一个 Task。

## 5. 关键场景

**A. 普通问题**
张三私聊「结算页 500 是不是上周发布引起的」→ 新 Task，分诊 deep → Worker 查日志，出草稿 → in_review（待发送），推卡片 → Yi 改一句点发送 → done。

**B. 起草中对方又补了一句**
Task 在 in_progress → 新消息追加，插进正在跑的 Run → 产出一份草稿回两条，不出两张卡。

**C. 草稿还没发，对方追问**
Task 在 in_review → 追加，回到 todo → 新 Run，草稿出 v2，旧版标「已被替换」→ 原卡片更新。

**D. Yi 自己先回了**
轮询看到 Yi 在这个会话里回复 → Router 过滤步判定「已亲自回复」→ 在跑的 Run 中止，Task done（原因：已亲自回复），卡片更新成「你已回复」。

**E. 要执行写操作**
Worker 要 `archery submit` → 守卫判 approve → Task blocked（待审批），卡片上是命令和理由 → Yi 批准 → cabinet 执行，结果追加 → 回到 todo，Worker 接着把结论写完 → in_review。

**F. 告警**
同一个群 3 分钟内来了 5 条告警 → 攒批，收口后建一个 Task 交给 alert → 结论：2 个根因，1 个已恢复 → in_review（看结论）→ 40 分钟后同群又来 2 条 → 追加到这个 Task，Worker 接着看。

**G. 失败**
Run 超时 → 自动重试（最多 2 次，额度类换备用模型）→ 还失败：Task blocked（失败），卡片上有「重试」「放弃」。

**H. 已经发完，三天内对方在同一话题回了**
Task 已 done → 话题内的消息在 3 天内重开同一个 Task（带着上次的会话和草稿），不当成新的一件事。私聊主线（没有话题）不重开，开新 Task。

## 6. 和现在的差异

| 现在 | 改后 | 影响 |
| --- | --- | --- |
| 草稿、agent 任务、问答、审批各有一套状态 | 都挂在 Task 上，看板只认 Task 的状态和 need | 看板分组清楚：等我 / 进行中 / 排队 / 完成 |
| 「建议不回」进待确认 | 直接 done，「今天完成」里能翻到、能撤回 | 少打扰（已确认，11-09） |
| 定时任务每次都私聊一张卡片 | 没有变化就 done，不推 | 少打扰（已确认，11-09） |
| 告警任务每轮结束都私聊（`notify: true`） | 只在需要 Yi 时推，同一 Task 更新原卡片 | 卡片变少 |
| 审批单独一张卡片 | 审批是 Task 的一个状态，卡片还是那张 | 来龙去脉在一处 |
| 草稿转任务新建一个 agent 任务 | 同一个 Task 换成 dev | 时间线连续 |
| 重开靠订阅（订阅挂会话） | 重开就是 Task 回到 todo，订阅表只做 thread → Task 的索引 | 概念少一个 |

不变的：分诊档位、助手 / dev / alert 三种 Worker、守卫和审批规则、「以 Yi 身份发出必须 Yi 确认」、durable 会话和重启接回。
